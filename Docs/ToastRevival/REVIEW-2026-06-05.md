## 1. Executive Summary

- **Live credentials on disk**: Plaintext server passwords, GitHub PATs (including repo-scoped private PATs), and production IPs exist in `Docs/ToastRevival/.env` and `.env.pats`. These files are gitignore-excluded but physically present alongside the repo; any zip/tarball or mirror sync accident exposes full source repository access and production SSH.
- **MFA elevation window is 32x too wide**: `docker-compose.yml` overrides the `Jwt__MfaElevationExpiresInMinutes` value to 480 minutes, completely defeating the intended 15-minute step-up security window enforced throughout `AuthController` and `SystemController`.
- **Multi-tenant isolation relies on a single implicit layer**: The EF Core global query filter is the *sole* tenant boundary on read paths for Devices, Notifications, Analytics, and DeviceGroups. No explicit `TenantId` predicate exists on these endpoints as a backstop. A single `IgnoreQueryFilters` call anywhere in those paths exposes cross-tenant data silently.
- **Authenticode revocation checking disabled**: Both agent update verifiers (`UpdateService` and `SelfUpdateService`) call `WinVerifyTrust` with `fdwRevocationChecks = 0`. A revoked Toast2IT signing certificate passes verification, enabling compromised-certificate update delivery to every enrolled device.
- **No CI/CD pipeline, no retry/circuit-breaker, no global exception handler**: The `.github/workflows/` directory is empty. All external HTTP calls (Mailjet, ClickSend, Stripe, Turnstile, Azure Content Safety) have no retry or circuit-breaker. An unhandled exception anywhere in the API produces an unstructured 500 with no central logging hook.

### Authentication & Authorization

#### ðŸŸ¡ Refresh token is opaque and never persisted â€” cannot be revoked
- **Location:** `TokenService.cs:57-60` â€” `CreateRefreshToken()`; `AuthController.cs` Login/VerifyLoginSms/VerifyLoginTotp responses
- **Detail:** `CreateRefreshToken()` returns 64 random bytes as a base64 string included in `AuthResponse` but never stored in the database. There is no token-exchange endpoint, no rotation, and no revocation path. The refresh token is decorative: clients storing it can never use it, but a future developer adding a `/api/auth/refresh` endpoint without a revocation table would issue permanently valid tokens.
- **Recommendation:** Either remove `refreshToken` from `AuthResponse` entirely or implement a full lifecycle: persist a SHA-256 hash in a `RefreshTokens` table with `UserId`, `ExpiresAt`, `RevokedAt`; add `POST /api/auth/refresh`; revoke on password reset and role change alongside `SecurityStamp` rotation.

#### ðŸŸ¡ SMS OTP brute-forceable when rate limiter resets
- **Location:** `AuthController.cs:526-563` (`VerifyLoginSms`), `681-726` (`MfaVerifySms`); `Program.cs` login-sms-per-ip policy: 5 attempts / 15 min
- **Detail:** The SMS OTP covers 1,000,000 values. An attacker distributing requests across 200,000 IPs can exhaust the full 6-digit space in a single 15-minute window against a known `UserId`. The `UserId` is disclosed in the `LoginSmsChallenge` response after a successful password check.
- **Recommendation:** Add a per-`UserId` rate limit on the SMS verify endpoint capped at 3-5 total attempts before the code is invalidated. Consider lengthening OTP to 8 digits.

#### ðŸŸ¡ Weak password minimum â€” 8 characters, no uppercase or special character required
- **Location:** `Program.cs:43-47` (Identity password options); `UserDtos.cs` `InviteUserRequest` `MinLength(8)`; `AuthDtos.cs` `SetPasswordRequest` `MinLength(8)`
- **Detail:** `RequireUppercase=false`, `RequireNonAlphanumeric=false`, `RequiredLength=8`. Password 'password1' satisfies these rules. MFA is not enforced by default (`RequireMfa` defaults to false) and is absent for accounts without a confirmed phone or TOTP secret â€” those accounts receive a JWT directly at login (line 519).
- **Recommendation:** Raise `RequiredLength` to 12, set `RequireUppercase=true` and `RequireNonAlphanumeric=true`. Alternatively, implement NIST SP 800-63B: check against a common-password blocklist.

#### ðŸŸ¡ MFA bypass: accounts without confirmed phone and without TOTP receive a JWT directly
- **Location:** `AuthController.cs:511-519` â€” the 'no phone confirmed' branch of Login
- **Detail:** After a successful password check, if neither TOTP nor a confirmed phone is present, the code falls through to issuing a full JWT with no second factor. Accounts created via `SystemController.CreateTenant` with `InitialPassword` set and accounts created via `InviteUserRequest` both start in this state, so all new accounts begin single-factor.
- **Recommendation:** For newly created or invited accounts, set an `MfaEnrollmentRequired` flag that forces the login flow to return a partial challenge requiring MFA enrollment before a full session token is issued.

#### ðŸŸ¡ Device token: 365-day lifetime with no stamp-based revocation caching
- **Location:** `TokenService.cs:43-54` â€” `CreateDeviceToken`; `Program.cs` JWT `ClockSkew=Zero`
- **Detail:** Device JWTs are issued with a 365-day expiry. Revocation requires a DB hit on every request (`IsDeviceRevoked`). The device token has no epoch/stamp claim analogous to the user `tokenEpoch`, so revocation cannot be cached. At fleet scale this creates per-request DB load with no cache path.
- **Recommendation:** Add a `DeviceSecurityStamp` claim to the device JWT mirroring the user `tokenEpoch` pattern. On decommission or re-register, rotate this value. Use a short-TTL cache to avoid per-heartbeat DB hits.

#### ðŸŸ¡ SSO callback delivers JWT in URL fragment
- **Location:** `SsoController.cs:217` â€” `Redirect($"{FrontendBase()}/sso/callback#token={Uri.EscapeDataString(jwt)}")`
- **Detail:** The full JWT (potentially MFA-elevated) is embedded in the URL fragment. Fragments are stored in browser session history, readable by any JavaScript on the page including third-party scripts, and capturable by browser extensions.
- **Recommendation:** Use a short-lived (60-second), single-use server-side exchange code instead of the JWT in the fragment. The SPA presents the code to `POST /api/auth/sso/microsoft/exchange` which issues the JWT in the response body.

#### ðŸŸ¡ Enrollment key reinstall carve-out (XT-M1) â€” spent token reusable by anyone knowing DeviceName + Username
- **Location:** `DevicesController.cs:719-737` â€” `PassesEnrollmentGateAsync` reinstall branch
- **Detail:** When a single-use token is already consumed, re-registration is allowed if the presented token matches `UsedByDeviceName` and `UsedByUsername`. Both values are self-reported. An attacker reading the token from HKLM plus knowing the original device name and Windows username can re-register the device identity. Severity is bounded by requiring local admin access.
- **Recommendation:** Track and accelerate XT-3: bind the enrollment token to the machine SID. On reinstall, require the re-presented machine SID to match the originally-bound SID.

#### ðŸŸ¢ SystemController read endpoints lack MFA step-up â€” cross-tenant PII exposed to session-only platform admin tokens
- **Location:** `SystemController.cs`: GET `trial-requests`, `tenants`, `tenants/{id}`, `billing-overview`, `users`, `devices`
- **Detail:** `RequireFreshMfa()` is correctly applied to all mutating platform-admin endpoints but not to read endpoints that expose full cross-tenant user PII (email, full name, role, MFA status), tenant financial data (Stripe IDs, MRR), and device inventory.
- **Recommendation:** Apply `RequireFreshMfa()` to GET `tenants/{id}`, GET `users`, and GET `billing-overview` at minimum.

#### ðŸŸ¡ BillingController Stripe config endpoint lacks MFA step-up
- **Location:** `BillingController.cs:76-97` â€” GET/POST `/api/billing/admin/stripe-config`
- **Detail:** `POST /api/billing/admin/stripe-config` accepts the Stripe secret key and writes it to config. Protected by `IsPlatformAdmin()` but no `RequireFreshMfa()` guard, unlike parallel `SystemController` endpoints. A compromised platform-admin session can rotate the Stripe secret key to an attacker-controlled value.
- **Recommendation:** Add `RequireFreshMfa()` to `POST /api/billing/admin/stripe-config`.

#### ðŸŸ¢ VerifySms (registration) does not call `RegisterFailedSmsAttemptAsync`
- **Location:** `AuthController.cs:135-165` â€” `VerifySms` (registration flow)
- **Detail:** The login SMS verify path correctly calls `RegisterFailedSmsAttemptAsync` on wrong code. The registration counterpart returns `Unauthorized` on wrong code but does not increment the lockout counter. An attacker can brute-force the 6-digit registration OTP without triggering lockout.
- **Recommendation:** Add `RegisterFailedSmsAttemptAsync` call in `VerifySms` on wrong-code branch. Apply the `login-sms-per-ip` rate limiter to `POST /api/auth/register/verify-sms`.

#### ðŸŸ¡ Notification target resolution (TargetType.Device) lacks explicit tenant check
- **Location:** `NotificationsController.cs:633-636` â€” `ResolveTargetDeviceIds` `TargetType.Device` branch
- **Detail:** The device target branch queries `_db.Devices.Where(d => d.Status == Active && TargetIds.Contains(d.Id))` relying entirely on the global filter for tenant isolation. The `TargetType.Group` branch already has explicit `d.TenantId == tenantId` predicates, making the inconsistency notable.
- **Recommendation:** Add explicit `.Where(d => req.TargetIds.Contains(d.Id) && d.TenantId == tenantId && d.Status == DeviceStatus.Active)`.

#### ðŸŸ¢ InviteUserRequest supplies a plaintext password in the request body
- **Location:** `UserDtos.cs:14-17` â€” `InviteUserRequest(Email, Password, Role)`; `UsersController.cs:70`
- **Detail:** Admin-created users receive their initial password in the request body. This password appears in any request logging middleware, APM traces, or structured log sinks that capture request bodies.
- **Recommendation:** Remove `Password` from `InviteUserRequest`. Create invited users with `RegistrationStep.PendingPasswordSet` and send a set-password link via email, mirroring `SystemController.ApproveTrialRequest`.

#### ðŸŸ¢ JWT algorithm not pinned in `TokenValidationParameters`
- **Location:** `Program.cs:104-114` â€” `TokenValidationParameters`; `TokenService.cs:93` â€” `HmacSha256`
- **Detail:** `TokenValidationParameters` does not set `ValidAlgorithms`. The library defaults to accepting any algorithm in the token header. With a symmetric key this is lower risk, but an explicit pin is RFC 8725 best practice.
- **Recommendation:** Add `ValidAlgorithms = new[] { SecurityAlgorithms.HmacSha256 }` to `TokenValidationParameters`.

#### ðŸŸ¢ CORS wildcard in Development â€” accidental production promotion risk
- **Location:** `Program.cs:342-348` â€” CORS configuration
- **Detail:** Development CORS allows any origin with credentials. A misconfigured `ASPNETCORE_ENVIRONMENT` (e.g., set to `Staging`) in a live environment would activate the wildcard policy.
- **Recommendation:** Add a startup validation in non-Development environments: if `AllowedOrigins` is null or empty, throw `InvalidOperationException`.

### Injection & Input Validation

#### ðŸŸ¡ Template URLs bypass `AbsoluteHttpUrl` validation and moderation scan
- **Location:** `TemplatesController.cs:65-70, 114-119`; `TemplateDtos.cs` (`CreateTemplateRequest` / `UpdateTemplateRequest`)
- **Detail:** `HeroImageUrl` and `LogoImageUrl` in template DTOs carry no `[AbsoluteHttpUrl]` annotation and no content-moderation scan. `SendNotificationRequest` correctly applies both. A template with `file://`, `\\UNC\share\`, or `javascript:` URLs can be saved and then serialised into a signed notification payload reaching every enrolled Windows agent.
- **Recommendation:** Apply `[AbsoluteHttpUrl]` to `HeroImageUrl` and `LogoImageUrl` in both template request DTOs. Add URL validation and optional moderation scan in `TemplatesController.Create`/`Update`.

#### ðŸŸ¡ `ToPublicUrl` trusts attacker-controlled `X-Forwarded-Host` header
- **Location:** `DevicesController.cs:640-659` (`ToPublicUrl`)
- **Detail:** When a stored asset URL is relative, `ToPublicUrl` builds an absolute URL by reading `X-Forwarded-Host` directly from raw request headers â€” not the `ForwardedHeaders`-validated `Request.Host`. An attacker with a device JWT can bake a hostile origin into `LogoUrl` and `LockScreenImageUrl` returned to the agent, creating a targeted SSRF/host-header injection.
- **Recommendation:** Replace the raw header reads with `Request.Scheme` and `Request.Host` (already validated by `ForwardedHeaders` middleware) or derive from the configured `App:BaseUrl`.

#### ðŸŸ¡ `EscapeCsvTitle` in `BuildDeliveryCsv` does not apply formula-injection protection
- **Location:** `NotificationsController.cs:450-453, 471`
- **Detail:** `EscapeCsvTitle` only doubles internal quotes â€” it does not prefix formula-trigger characters (`=`, `+`, `-`, `@`, `\t`, `\r`) with an apostrophe. The notification title is also written un-sanitised into the comment header line without quoting, so a title containing a comma or newline breaks the comment structure.
- **Recommendation:** Replace `EscapeCsvTitle` with a call to `CsvHelper.Cell` or apply `IsFormulaTrigger` prefix logic before quoting.

#### ðŸŸ¡ `ActionButtonsJson` on templates stored without structural validation
- **Location:** `TemplatesController.cs:70, 119`
- **Detail:** `ActionButtonsJson` is accepted as a raw string and written directly to the database without parsing, URL allow-list check, or button count limit. The notification send path passes `ActionButtons` through `TryNormalizeActionButtons`, which enforces a 3-button cap, validates label/actionId length, and enforces `http(s)` URLs. Templates bypass all these guards.
- **Recommendation:** Run `ActionButtonsJson` through `TryNormalizeActionButtons` (or equivalent) in `TemplatesController.Create` and `Update` before persisting.

#### ðŸŸ¢ CSP `script-src` allows `'self'` without nonce or hash
- **Location:** `Program.cs:427-432`
- **Detail:** If an attacker places a `.js` file anywhere under served static paths, that script executes in the SPA context. The `img-src 'self' data: https:` allows any `https:` image URL including attacker-controlled ones. `'unsafe-inline'` on `style-src` is wider than necessary for a JSON API.
- **Recommendation:** For the React SPA, consider nonce-injected or hash-based `script-src` (Vite supports this). For API-only responses, tighten `img-src` to a CDN/assets domain allowlist.

#### ðŸŸ¢ Device registration accepts unbounded `DeviceName` and `Username` fields
- **Location:** `DeviceDtos.cs:5-11` (`RegisterDeviceRequest`); `DevicesController.cs:59-165`
- **Detail:** Both fields carry `[Required]` but no `[MaxLength]`. The registration endpoint is anonymous. Multi-MB device names can consume database space and disrupt CSV export or dashboard rendering.
- **Recommendation:** Add `[MaxLength(256)]` to both fields. Trim both in the `Register` action before the idempotent lookup.

#### ðŸŸ¢ SSO callback emits JWT in URL fragment (duplicate of Auth finding â€” injection angle)
- **Location:** `SsoController.cs:217`
- **Detail:** Token is accessible to JavaScript on the callback page. If the React app reads `location.hash` before clearing it, third-party scripts can observe it.
- **Recommendation:** Ensure `/sso/callback` calls `history.replaceState('')` immediately after reading the fragment. Consider short-lived one-time code exchange.

#### ðŸŸ¢ Enrollment token reinstall carve-out relies on self-reported identity (duplicate â€” injection angle)
- **Location:** `DevicesController.cs:719-737`
- **Detail:** `DeviceName` and `Username` are both self-reported. No hardware binding. Per XT-M1 comment, fix planned for XT-3.
- **Recommendation:** Log a warning-level audit event whenever the carve-out path is taken until XT-3 ships.

#### ðŸŸ¢ Token stored in `localStorage` accessible to any JavaScript on the origin
- **Location:** `client.ts:7-8` (`getToken` / `localStorage`)
- **Detail:** Any XSS vulnerability allows token exfiltration. React JSX escaping is a strong default guard but `localStorage` is directly accessible from JavaScript.
- **Recommendation:** Ensure all server-rendered or dynamically-inserted content is rendered via React JSX (not `dangerouslySetInnerHTML`). Evaluate `HttpOnly` cookie-based storage if a BFF pattern is viable.

#### ðŸ”µ Missing CSRF protection on state-mutating SPA calls
- **Location:** `client.ts` (all POST/PUT/PATCH/DELETE calls)
- **Detail:** Bearer-only authentication means same-site CSRF is not a current risk. However, any future cookie-based auth path would have no CSRF protection.
- **Recommendation:** Document the Bearer-only assumption explicitly. Ensure any future cookie-based auth includes `SameSite=Strict` or an anti-CSRF token.

### Abuse-Case / DoS Protection

#### ðŸŸ  `forgot-password` is an uncapped email-cost amplifier
- **Location:** `AuthController.cs` â€” `POST /api/auth/forgot-password` (line 202)
- **Detail:** No rate-limiting attribute and no Turnstile challenge. An attacker can POST a valid email in a tight loop, causing continuous `GeneratePasswordResetTokenAsync` calls and Mailjet email dispatches. Drains email quota and constitutes targeted harassment against any known user email.
- **Recommendation:** Add `[EnableRateLimiting("login-per-ip")]` to `POST forgot-password`. Optionally add a lightweight Turnstile check matching the `/register/init` pattern.

#### ðŸŸ  `register/verify-sms` has no rate limit on OTP guessing
- **Location:** `AuthController.cs` â€” `POST /api/auth/register/verify-sms` (line 135)
- **Detail:** Missing `[EnableRateLimiting]` entirely. `RegisterFailedSmsAttemptAsync` is NOT called on wrong code. A 6-digit OTP has 10^6 space; an attacker faces no per-IP throttle and no lockout â€” effectively unlimited guesses within the 10-minute OTP window.
- **Recommendation:** Add `[EnableRateLimiting("login-sms-per-ip")]`. Call `RegisterFailedSmsAttemptAsync` on wrong-code branch.

#### ðŸŸ¡ Turnstile bypass: `IsEnabled=false` silently allows all traffic in some configurations
- **Location:** `CloudflareTurnstileVerifier.cs:39-48`; `AuthController.cs:82`
- **Detail:** `CloudflareTurnstileVerifier` is registered as transient and re-reads config on each request scope. If `appsettings.Local.json` reloading blanks the keys at runtime, `IsEnabled` may flip without a restart. Behavior on misconfiguration is fail-closed but not loudly signaled at boot.
- **Recommendation:** Add a startup validation throwing if `Turnstile:SiteKey` or `Turnstile:SecretKey` are absent in non-Development environments, mirroring the `Jwt:Key` check.

#### ðŸŸ¡ Unbounded notification queue channel â€” no depth cap or back-pressure
- **Location:** `NotificationQueueService.cs:22`
- **Detail:** `Channel.CreateUnbounded`. `Enqueue()` calls `TryWrite` unconditionally and can never fail. A burst of large `TargetType.All` blasts piles up. No maximum queue depth and no shed mechanism. The health endpoint exposes `QueueDepth` but nothing alerts on it or triggers 429 responses.
- **Recommendation:** Switch to `Channel.CreateBounded` (e.g., 10,000 items) with `QueueProcessingOrder.OldestFirst`. Return 503 from the Send endpoint on `TryWrite` failure.

#### ðŸŸ¡ `forgot-password` is a user-existence timing oracle
- **Location:** `AuthController.cs:202-220` â€” `ForgotPassword`
- **Detail:** When the email IS found, the code calls `GeneratePasswordResetTokenAsync` and `SendAsync` (Mailjet I/O). When NOT found, the path returns immediately. The observable response-time difference can enumerate valid email addresses over many requests.
- **Recommendation:** Add a constant-time delay (e.g., `await Task.Delay(250)`) on the early-return path so both branches complete at approximately the same wall-clock time.

#### ðŸŸ¡ Device registration exposes tenant existence before enrollment gate
- **Location:** `DevicesController.cs:62-64` â€” `POST /api/devices/register`
- **Detail:** When `TenantId` is not found, the endpoint returns 404 'Tenant not found.' before checking the enrollment key. An unauthenticated attacker can enumerate valid tenant GUIDs by comparing 404 vs 403 responses.
- **Recommendation:** Return a uniform 403 for both 'tenant not found' and 'invalid enrollment key' cases.

#### ðŸŸ¡ `POST /api/auth/mfa/send-sms` has no per-user SMS send-rate cap
- **Location:** `AuthController.cs:636-671`
- **Detail:** Only per-IP limiting. An authenticated attacker rotating source IPs can trigger unlimited ClickSend SMS sends with no per-user or per-phone-number cap.
- **Recommendation:** Add a per-`userId` rate limit (e.g., 3 sends per 30 minutes) enforced via `IMemoryCache` keyed on `userId`.

#### ðŸŸ¡ Audit log export has no row count cap â€” can generate arbitrarily large PDF/CSV responses
- **Location:** `AuditController.cs:70-107` â€” GET `/api/audit/export`
- **Detail:** Fetches the FULL audit log for up to 90 days with no `Take`/limit applied. For a high-volume tenant this could be tens of thousands of rows materialized into memory and serialized into a QuestPDF PDF.
- **Recommendation:** Apply a maximum row count cap (e.g., 50,000 rows) via `.Take()` before materializing. Return a truncation header if the cap is hit. Consider streaming pagination for PDF.

#### ðŸŸ¢ Stripe webhook endpoint reads unbounded request body
- **Location:** `BillingController.cs:242-292`
- **Detail:** `[DisableRateLimiting]` and `[AllowAnonymous]` required for Stripe delivery. Body is read via `StreamReader` with no explicit size limit before signature verification. A large forged POST can consume significant server I/O and memory before being rejected.
- **Recommendation:** Add `[RequestSizeLimit(65536)]` (64 KB is more than enough for any Stripe event).

#### ðŸŸ¢ Stripe webhook handler has no idempotency guard against duplicate events
- **Location:** `BillingController.cs:291`; `HandleStripeEventAsync:297-332`
- **Detail:** `Task.Run` fires the handler asynchronously. Stripe can deliver the same event multiple times. `HandleCheckoutCompleted` and `HandleInvoicePaid` apply changes without checking whether the event was already applied (`evt.Id` never stored).
- **Recommendation:** Persist processed `evt.Id` values in a DB table and check for duplicates at the start of `HandleStripeEventAsync`.

#### ðŸŸ¢ Health endpoint exposes queue depth and DB latency to unauthenticated callers
- **Location:** `HealthController.cs` â€” GET `/api/health`
- **Detail:** Response includes `queueDepth`, `uptimeSeconds`, and `db.latencyMs`. These collectively help an attacker fingerprint deployment state and time targeted requests during queue saturation or post-restart windows.
- **Recommendation:** Expose only binary healthy/unhealthy to public probes. Move detailed subsystem metrics behind an authenticated endpoint or a configurable secret token header.

#### ðŸŸ¢ Analytics controller materializes full delivery status arrays without a time-window row cap
- **Location:** `AnalyticsController.cs:46-50` (Summary); `104-107` (Breakdown)
- **Detail:** `SELECT d.Status ... ToListAsync()` with no `Take()` cap. For a large tenant with millions of deliveries, this materializes a large enum list into API process memory.
- **Recommendation:** Perform aggregation server-side with `GroupBy().Count()` queries. This is idiomatic EF and eliminates the unbounded memory risk.

### Multi-Tenant Architecture

#### ðŸ”´ Global query filter is null-transparent â€” comment says 'null means no filter' but runtime behavior is 'null returns empty set'
- **Location:** `AppDbContext.cs:43,53,62,79,88,101,117,126,152,165,182`; `ITenantProvider.cs:7`
- **Detail:** `ITenantProvider.TenantId` is declared nullable (`Guid?`). EF Core global query filters expressed as `e.TenantId == _tenantProvider.TenantId` translate `null == null` to `WHERE TenantId IS NULL` in SQL â€” returning zero rows, not unfiltered data. The comment in `ITenantProvider.cs` says 'null as no filter' which is factually wrong. Background services or webhook handlers using the same `DbContext` without a tenant identity will receive empty result sets, masking bugs silently. Any code intentionally relying on 'null means no filter' behavior will fail silently.
- **Recommendation:** Correct the comment in `ITenantProvider.cs` to match runtime reality. Add integration tests exercising device-token-typed requests against tenant-filtered endpoints. For tables explicitly intended to be readable cross-tenant, update filters to `e.TenantId == _tenantProvider.TenantId || _tenantProvider.TenantId == null`.

#### ðŸŸ  `DevicesController.List` and `.Get`: global filter is the only tenant guard
- **Location:** `DevicesController.cs:170-193`
- **Detail:** Both endpoints rely entirely on the EF Core global filter for tenant isolation. No explicit `d.TenantId == tenantId` predicate. Mutation endpoints (Decommission, RequestUninstall, etc.) all read `TenantId` from the JWT and explicitly check. The read-only list endpoints have no such backstop.
- **Recommendation:** Add explicit tenant predicate: `_db.Devices.Where(d => d.TenantId == tenantId && d.Status != DeviceStatus.Decommissioned)`.

#### ðŸŸ  `NotificationsController.History`: missing tenant predicate
- **Location:** `NotificationsController.cs:243-267`
- **Detail:** `GET /api/notifications` queries `_db.Notifications` with only `.OrderByDescending(n => n.CreatedAt)` and no explicit `n.TenantId == tenantId` predicate. Tenant isolation entirely delegated to the EF Core global filter.
- **Recommendation:** Read `tenantId` from JWT claims and add `.Where(n => n.TenantId == tenantId)` to the History query.

#### ðŸŸ  `AnalyticsController`: all three analytics endpoints lack explicit `TenantId` predicates
- **Location:** `AnalyticsController.cs:34-131`
- **Detail:** `Summary`, `Volume`, and `Breakdown` all query without explicit `TenantId` predicates. The comment in `Breakdown` explicitly states 'Both sides carry global tenant query filters so no explicit TenantId filter needed' â€” incorrect architectural reasoning. A broken filter would silently blend cross-tenant metrics.

#### ðŸŸ  `DeviceGroupsController.AddMember`: device existence check has no tenant scope
- **Location:** `DeviceGroupsController.cs:127-129`
- **Detail:** `AddMember` checks `_db.Devices.AnyAsync(d => d.Id == req.DeviceId && d.Status != DeviceStatus.Decommissioned)` relying on the global filter. `SetMembers` (lines 160-165) validates device IDs against `_db.Devices` without explicit `d.TenantId == tenantId`.

- **Location:** `NotificationsController.cs:625-647`
- **Detail:** Both branches rely solely on the global filter. The base query `_db.Devices.Where(d => d.Status == DeviceStatus.Active)` has no explicit `.Where(d => d.TenantId == tenantId)`. #### ðŸŸ¡ `DeviceGroupMember` has no own `TenantId` column â€” filter is derived via navigation join
- **Location:** `Models/DeviceGroupMember.cs`; `AppDbContext.cs:65-80`

#### ðŸŸ  Analytics summary materializes all delivery status rows into memory
- **Location:** `AnalyticsController.cs`, `Summary()` â€” lines 46-51; `Breakdown()` â€” line 104
- **Detail:** `_db.NotificationDeliveries.Where(d => d.CreatedAt >= since).Select(d => d.Status).ToListAsync()` pulls every delivery status enum for the period into the .NET process then counts with in-process LINQ. - **Location:** `AuditController.cs`, `Export()` â€” lines 86-89
- **Detail:** `ToListAsync()` loads all matching rows for the requested period into `List<AuditLog>` before calling `GenerateAuditLogPdf` or `BuildAuditCsv`. Each row carries the full `DetailsJson` blob. A single export request can spike memory by hundreds of MB.

#### ðŸŸ  `PdfExportService.GenerateAuditLogPdf` and `GenerateDeliveryReportPdf` block the request thread
- **Location:** `PdfExportService.cs`, both `GenerateAuditLogPdf()` and `GenerateDeliveryReportPdf()`
- **Detail:** Both methods are fully synchronous (`byte[]` return, no async) and run entirely on the calling thread pool thread. QuestPDF's `GeneratePdf()` is CPU-intensive. Under load, concurrent export requests can exhaust the thread pool and cause queuing.

- **Location:** `AuditService.cs`, `LogAsync()` â€” lines 18-33

#### ðŸŸ¡ `NotificationQueueService` uses an unbounded channel with no backpressure

### Reliability

#### ðŸŸ  No global exception handler middleware in `Program.cs`
- **Location:** `Program.cs`
- **Detail:** No `UseExceptionHandler` or equivalent global middleware. Unhandled exceptions surface as raw 500s with no central logging hook, no structured error response, no single point for monitoring. A `DbUpdateException` from a race condition or an `ArgumentNullException` in a service constructor propagates to Kestrel unhandled.
- **Recommendation:** Add `app.UseExceptionHandler("/error")` or use the built-in ProblemDetails middleware via `services.AddProblemDetails()`. This provides structured error logging and consistent RFC 7807 responses for all unhandled exceptions.

#### ðŸŸ  Fire-and-forget Stripe webhook handler with no unobserved-exception guarantee
- **Location:** `BillingController.cs:291`
- **Detail:** `_ = Task.Run(...)` â€” if the thread-pool Task faults before reaching `HandleStripeEventAsync` (e.g., `ObjectDisposedException` on app shutdown), the exception is unobserved and silently lost. No backpressure: a burst of webhook events can queue unlimited thread-pool tasks contending on the same DB connection pool.
- **Recommendation:** Use `IHostedService` or a Channel-based background queue. Store the raw Stripe event to DB first and process asynchronously, providing an audit trail and retry surface. If fire-and-forget is kept, wrap in a tracked background task with `IHostApplicationLifetime`.

#### ðŸŸ  No retry logic on Mailjet or ClickSend HTTP calls
- **Location:** `MailjetEmailService.cs:44`; `ClickSendSmsService.cs:41`
- **Detail:** Both call `PostAsync` and `EnsureSuccessStatusCode` with no retry policy. A transient network hiccup or provider 429/5xx immediately throws `HttpRequestException`. For SMS in the login flow, this means users cannot complete MFA login during a ClickSend momentary failure. Neither service has a timeout beyond the default 100s, so a hung connection holds a request thread for nearly two minutes.
- **Recommendation:** Register both HttpClients with Polly retry + circuit-breaker via `AddPolicyHandler` in `Program.cs`. Pattern: 3 retries with exponential backoff for 5xx/timeout, circuit-breaker opens after 5 consecutive failures. Set `HttpClient.Timeout` to 15s on each client.

#### ðŸŸ¡ No retry logic on Stripe API calls in `BillingController` and `StripeBillingSyncService`
- **Location:** `BillingController.cs:158, 192, 219`; `StripeBillingSyncService.cs:32-44`
- **Detail:** All Stripe SDK calls are bare awaits with no retry. Stripe SDK does not retry by default. A transient error on checkout or portal creation returns a 500 to the user. `BillingController.CreateCheckout` and `CreatePortal` have no `try/catch` at all â€” any `StripeException` propagates to Kestrel.
- **Recommendation:** Add `try/catch` around Stripe calls in `CreateCheckout` and `CreatePortal`, returning user-friendly 503 on transient failures. Consider Polly retry on the underlying HttpClient.

#### ðŸŸ¡ No circuit breaker for any external HTTP dependency
- **Location:** `MailjetEmailService.cs`, `ClickSendSmsService.cs`, `CloudflareTurnstileVerifier.cs`, `ContentSafetyService.cs`, `MicrosoftSsoService.cs`
- **Detail:** None of the five external HTTP integrations have a circuit breaker. A prolonged provider failure causes every request on that path to wait for the full HTTP timeout (default 100s), potentially exhausting the thread pool or DB connection pool. Turnstile failure effectively blocks all registrations until the circuit reopens.
- **Recommendation:** Use Polly circuit breaker (or `Microsoft.Extensions.Http.Resilience` in .NET 8) on all five `HttpClient` registrations. Pattern: open after 3 failures in 30s, stay open for 30s. Pair with a timeout policy (5-10s per call).

#### ðŸŸ¡ `HttpContextTenantProvider` / content moderation service has a growing static client cache
- **Location:** `ContentSafetyService.cs:44-58`; `Program.cs:312`
- **Detail:** `ConcurrentDictionary<string, ContentSafetyClient>` is a static field, so `ContentSafetyClient` instances are never evicted. If a tenant rotates their `ModerationCustomKey`, the old client stays in memory forever alongside the new client. Under heavy tenant churn, this is a slow memory leak.
- **Recommendation:** Replace with `IMemoryCache<string, ContentSafetyClient>` with a sliding expiry (e.g., 1 hour). Allows stale entries to be evicted after key rotation.

#### ðŸŸ¡ `UpdateService.GetFeedUrl()` swallows all exceptions with an empty catch block
- **Location:** `UpdateService.cs:73-76`
- **Detail:** Catch block is `catch { /* fall through to default */ }`. Silences any exception including `OutOfMemoryException` and `ThreadAbortException`. A registry ACL denial or corrupted value will never be surfaced in `DiagLog`, making it invisible in field diagnostics.
- **Recommendation:** Add `catch (Exception ex)` with a `DiagLog.Write` line, matching the pattern used in `IsAutoUpdateEnabled`.

#### ðŸŸ¡ No React error boundary anywhere in the application
- **Location:** `Dashboard/src/App.tsx`; `Dashboard/src/main.tsx`
- **Detail:** The entire React tree has no `ErrorBoundary`. A runtime JavaScript error in any component (null-deref on unexpected API shape, failed lazy import, Recharts rendering error) unmounts the entire application displaying a blank screen.
- **Recommendation:** Add a class-based `ErrorBoundary` (or `react-error-boundary`) wrapping the `RouterProvider` in `App.tsx`, displaying a 'Something went wrong â€” refresh the page' fallback. Add per-route error boundaries for lazy-loaded chunks.

#### ðŸŸ¡ `handleRemoteUninstall` in `Devices.tsx` rethrows without setting error state
- **Location:** `Dashboard/src/pages/Devices.tsx:182-190`
- **Detail:** `try/finally` but no `catch`. The `RemoveAgentModal` receives `onRemoteUninstall={() => handleRemoteUninstall(removeTarget.id)}` â€” a fire-and-forget arrow function. If the modal does not internally catch, the rejection is silently swallowed. No page-level error state is set.

#### ðŸŸ¢ Stripe `UpdateManager` created fresh on every `ApplyUpdateAndRestart` call without timeout

### Windows Endpoint Security

#### ðŸŸ  `WinVerifyTrust` called with `fdwRevocationChecks = 0` in both Authenticode verifiers
- **Location:** `UpdateService.cs:264`; `SelfUpdateService.cs:706` â€” `WINTRUST_DATA.fdwRevocationChecks = 0`
- **Detail:** Both the Velopack-redirect verifier (`UpdateService.IsSignedByToast2IT`) and the MSI-update verifier (`SelfUpdateService.IsSignedByToast2IT`) call `WinVerifyTrust` with `WTD_REVOKE_NONE`. A Toast2IT code-signing certificate that has been compromised and subsequently revoked by Sectigo will still pass this gate. This is especially critical for the MSI path, which results in SYSTEM-level `msiexec` execution.
- **Recommendation:** Set `fdwRevocationChecks` to `WTD_REVOKE_WHOLECHAIN (0x00000002)` in both `WINTRUST_DATA` structs. Accept `CRYPT_E_NO_REVOCATION_CHECK` or `CRYPT_E_REVOCATION_OFFLINE` as a warning if offline scenarios must be supported, but do not unconditionally disable revocation.

#### ðŸŸ¡ Tenant logo download has no content-type or magic-byte validation
- **Location:** `TenantLogoStore.cs:70-77` (`DownloadAsync` / `ResolveExtension`)
- **Detail:** File extension derived solely from URL path segment. No `Content-Type` header check and no magic-byte validation. A tenant-controlled response could deliver any byte sequence (SVG with embedded script, XML, PE binary) while the URL ends in `.png`. `ReadAsByteArrayAsync` fully buffers the download before the size check, allowing a slow-drip server to consume up to 4 MB of heap.
- **Recommendation:** Check `Content-Type` response header against allowlist (`image/png`, `image/jpeg`). Validate first 8 bytes against known PNG (`\x89PNG`) and JPEG (`\xFF\xD8\xFF`) magic sequences. Use `ReadAsStreamAsync` with a length-limited copy.

#### ðŸŸ¡ `UpdateFeedUrl` for Velopack read from HKLM without schema enforcement â€” HTTP feed URL accepted
- **Location:** `UpdateService.cs:67-77` (`GetFeedUrl`)
- **Detail:** The registry value is returned without validating the scheme. An `http://` URL in the registry creates a downgrade-to-cleartext vector â€” an on-path attacker can substitute a malicious update package. The MSI path (`SelfUpdateService.DownloadAndVerifyMsiAsync`) has a correct DEBUG/RELEASE guard rejecting `http://` in production; `UpdateService.GetFeedUrl` has no equivalent.
- **Recommendation:** Validate the registry-sourced feed URL in `GetFeedUrl`: reject any scheme other than `https` in non-DEBUG builds. Log and fall back to `DefaultFeedUrl` when the registry value fails this check.

#### ðŸŸ¡ HMAC signing key stored in `config.json` with DPAPI `CurrentUser` scope â€” accessible to any process running as the same OS user
- **Location:** `DeviceConfig.cs:20` (signingKey field); `ConfigStore.cs:98-99` (DPAPI protect/unprotect)
- **Detail:** DPAPI `CurrentUser` scope prevents other OS user accounts and SYSTEM from reading the ciphertext but any process running in the same Windows session under the same user account can decrypt `config.json`. Once the signing key is extracted, an attacker can forge HMAC-valid notification payloads.
- **Recommendation:** Document the threat boundary explicitly. Consider adding a machine-tied entropy blob (`DataProtectionScope.LocalMachine` combined with a secret machine-unique GUID stored in HKLM with ACL-restricted access) for defense-in-depth. Implement server-driven signing-key rotation.

#### ðŸŸ¡ No certificate pinning on any HTTPS connection â€” agent trusts the OS certificate store
- **Location:** `AgentClient.cs:28, 83, 130, 260`; `SelfUpdateService.cs:522`; `TenantLogoStore.cs:52`
- **Detail:** Every `HttpClient` in the agent uses the default `HttpClientHandler` without any pinning. In MSP/enterprise environments, corporate SSL inspection proxies (Zscaler, Palo Alto, etc.) installed as trusted roots would intercept all agent connections transparently. An attacker with such a proxy can intercept HMAC signing keys received at registration.
- **Recommendation:** Implement SPKI hash pinning for `RegistrationService` and `AgentHubClient`. For MSI download, at minimum enforce hostname matching an expected domain suffix. Store pinned SPKI in HKLM registry key so MSPs can update without a full agent rebuild.

#### ðŸŸ¡ `ToastUrlLauncher` opens `http://` and `https://` URLs via `ShellExecute` with no hostname allowlist
- **Location:** `AgentClient.cs:752-790` (`ToastUrlLauncher.OpenIfAllowed`)
- **Detail:** Scheme restriction to `http`/`https` is correct and prevents `file://` and similar vectors. However, `UseShellExecute = true` invokes whatever application is registered as the default http/https handler. On endpoints where a browser with known vulnerabilities is the default handler, or where a malicious application has registered itself as the http handler, the agent becomes the delivery mechanism. The URL is derived from server-controlled notification payload (HMAC-signed).
- **Recommendation:** Consider maintaining an allowlist of permitted URL hostname suffixes per-tenant. Add a user-visible confirmation dialog for external URLs. Log the full URL for post-incident audit.

#### ðŸŸ¡ Trigger file for SYSTEM-executed `msiexec` written to world-writable `%ProgramData%` directory
- **Location:** `SelfUpdateService.cs:572-578` (`WriteTrigger`); line 191 (`RunUpdaterMode` reads trigger)
- **Detail:** `WriteTrigger` writes `pending-action.txt` to `%ProgramData%\Toast2IT\Toast Notification\` â€” a directory the interactive user created and can write to. The SYSTEM task reads this file. The update path re-verifies the staged MSI via Authenticode, but for the uninstall path, the product code is only GUID-validated by regex. #### ðŸŸ¢ `sign-msix.ps1` uses `signtool /a` (auto-select) â€” no thumbprint pinning of the signing certificate

- **Detail:** `signtool /a` auto-selects the best-matching certificate. On a developer machine with multiple code-signing certificates installed, `/a` could select an unintended certificate. - **Location:** `Program.cs:705`
- **Detail:** Writes to `%TEMP%\toastnotification-diag.txt` with no explicit security descriptor. Predictable filename allows any process running as the same user to read or overwrite it while being written. Log content includes device IDs, server URLs, connection states, and timing information.
- **Recommendation:** Use a randomly named temp file (`Path.GetTempFileName`) or write to a user-scoped path with an explicit restrictive ACL. Alternatively, stream directly to stdout without an intermediate temp file.

## 4. Top 10 Priority Fixes

1. **Rotate the GitHub PATs and server password in `Docs/ToastRevival/.env` and `.env.pats` immediately.** The private PAT has `repo` scope on the source repository; any accidental staging or mirror sync exposes full source access and production SSH. Add `git-secrets` or `truffleHog` as a pre-commit hook.

2. **Fix `Jwt__MfaElevationExpiresInMinutes: 480` in `docker-compose.yml` to 15.** This single line completely defeats the MFA step-up security model that `RequireFreshMfa()` guards are designed to enforce across SystemController and BillingController. All platform admin operations requiring fresh MFA are currently subject to 8-hour elevated tokens.

3. **Add explicit `TenantId` predicates to `AnalyticsController` (all three endpoints), `NotificationsController.History`, `DevicesController.List`/`Get`, `DeviceGroupsController.AddMember`/`SetMembers`, and `NotificationsController.ResolveTargetDeviceIds` (`TargetType.All`/`TargetType.Device` branches.** The current architecture has a single implicit layer for tenant isolation on these read and targeting paths. A filter misconfiguration or a future `IgnoreQueryFilters` call would expose cross-tenant data silently.

4. **Set `WinVerifyTrust` `fdwRevocationChecks` to `WTD_REVOKE_WHOLECHAIN (0x00000002)` in both `UpdateService` and `SelfUpdateService`.** Revocation checking is disabled entirely. A compromised and revoked Toast2IT signing certificate silently passes the gate, enabling compromised-certificate update delivery to every enrolled device â€” with the MSI path resulting in SYSTEM-level execution.

5. **Add `UseExceptionHandler`/`AddProblemDetails` global middleware and adopt RFC 9457 ProblemDetails uniformly across all controllers.** The API currently has no central exception handling, produces at least four distinct error shapes, and swallows unhandled exceptions. This blocks all error monitoring and makes client error parsing a fragile maintenance burden.

6. **Add Polly retry + circuit-breaker to Mailjet, ClickSend, Stripe, Turnstile, Azure Content Safety, and Microsoft Entra `HttpClient` registrations.** Currently any of the five external HTTP dependencies entering a failure state holds request threads for up to 100 seconds, potentially exhausting the thread pool. MFA login is blocked during ClickSend outages.

7. **Add `[EnableRateLimiting("login-sms-per-ip")]` and `RegisterFailedSmsAttemptAsync` to `POST /api/auth/register/verify-sms`, and add `[EnableRateLimiting("login-per-ip")]` to `POST /api/auth/forgot-password`.** Both endpoints are currently undefended: the registration OTP path has no rate limit and no lockout counter, and forgot-password has no rate limit and acts as an uncapped email-cost amplifier.

8. **Replace the SSO callback JWT fragment delivery with a short-lived one-time code exchange via `POST /api/auth/sso/microsoft/exchange`.** The current implementation places a full session JWT (potentially MFA-elevated) in the browser URL bar, session history, and in scope of all JavaScript on the callback page. This is a full account takeover vector if any script on the page reads `location.hash`.

9. **Add a `.dockerignore` file and configure the `Dockerfile` to emit no PDB files in the Release image.** Currently the build context includes `Docs/` (containing plaintext credentials), `scripts/`, and `.env.pats`. PDB files in the production container map IL offsets to source paths, lowering the bar for targeted exploitation of any container escape or registry breach.

10. **Create a minimal `ci.yml` GitHub Actions workflow running `dotnet build` and `dotnet test` on every push/PR to main.** The `.github/workflows/` directory is completely empty. There is no automated gate preventing a breaking change from merging, and no automated verification that the codebase builds or that tests pass.

## 5. Positive Observations

**Defense-in-depth where it is applied is solid.** The `RequireFreshMfa()` pattern on SystemController write operations, the HMAC-signed agent notification payloads, the Cloudflare Turnstile on the trial registration path, the per-IP and per-tenant rate limiting, and the Content Safety moderation with an admin blocklist layer are all genuine, well-implemented security controls. The code shows awareness of attack surfaces.

**EF Core global query filters are consistently applied across 11+ entity types.** The tenant isolation architecture is coherent; the findings above are defence-in-depth gaps against the filter being bypassed, not evidence that tenant isolation is fundamentally broken. The approach is sound and the filter definitions are correct.

**The agent Authenticode verification uses `WinVerifyTrust` directly (not `Get-AuthenticodeSignature`) and validates chain trust against the expected Subject CN.** This is the correct approach for SYSTEM-level MSI installation verification. The gap (revocation disabled) is fixable without rearchitecting.

**The notification queue pattern is well-structured.** `NotificationQueueService` with a background `IHostedService`, orphan recovery on startup, and the SignalR hub push with catch-up polling for offline devices is a solid design. The concerns raised (unbounded channel, individual delivery retry) are refinements to a good foundation.

**The prerender SEO architecture is the right approach for a React SPA.** Building static HTML at deploy time rather than relying on server-side rendering or JavaScript-required crawling demonstrates sound SEO engineering. The gaps identified are content depth issues, not architectural problems.

**Build scripts are well-organized and maintainable.** `build-msi.ps1`, `build-msix.ps1`, `build-release.ps1`, and `sign-msix.ps1` all use `$ErrorActionPreference = "Stop"`, post-step verification, and clear step commentary. The `sync-public-mirror.ps1` credential-sanitisation approach is thoughtful â€” the gap is only the `ErrorActionPreference` override.

**The `MfaService.VerifyAndClaimAsync` replay-guard pattern** (storing a one-time claim in the database and atomically comparing-and-deleting) is correct and race-condition-safe. This is easy to get wrong and it was done right.

**Structured audit logging via `AuditService`** with explicit `TenantId`, actor email, action type, and `DetailsJson` is a good foundation for compliance reporting. The export functionality (CSV and PDF) adds direct operational value for MSPs.
